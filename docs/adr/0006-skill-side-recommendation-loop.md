# Skill-side recommendation loop over deterministic service primitives

Deck recommendation is not a service capability. The build-from-collection flow is a loop the consuming agent drives: generate candidates from the index under collection scope, assemble a decklist with model-side judgment, evaluate, swap, repeat. The service exposes exactly what the vision's layer table names — index and simulation — plus one dedicated deterministic query (commander alternatives). A service-side `/optimize` endpoint was rejected: deck composition needs synergy and archetype judgment that lives in the model, not in deterministic code, and encoding it service-side would grow a search-heuristics layer the service cannot ground. The service's job is grounding — legality, retrieval, probabilities; the skill's job is choosing.

The loop's economics follow from that split. The only expensive operation is a tier-2 simulate call, so the iteration budget is a declared skill-side cap on tier-2 calls (default 10–20, stated in the answer), never a service knob. Every candidate passes a cheap gate first — the tier-1 screen (pip supply vs demand, category draw odds) and bracket classification — and only a passer spends a simulate call. Tier 1 suffices whenever the question is about mana and card categories; tier 2 is required the moment the goal names card semantics or sequencing. The loop has four stopping criteria. Three stop it: target met, plateau, and budget exhausted. Target met means the 95% CI lower bound of the goal floor reaches the skill's declared target. Plateau means three swap rounds without a rise in that lower bound. On plateau and budget exhausted the skill reports best-so-far and states the gap. Before the skill declares success, a fresh-seed confirmation run checks the winner against seed overfitting.

The fourth criterion, target out of reach, is a declaration, not a stop. The skill declares it once, before the first simulate call, when the reach bound (see `GLOSSARY.md`) is below the target. The loop then keeps the base seed and raises the lower bound until plateau or budget exhausted. It never declares success, so it spends no confirmation call. A best-so-far answer below the target still has value, as one recorded answer at 0.189 shows. The tier-1 category probability alone is not a bound, because the engine mulligans. A goal piece in the command zone has no reach bound.

The skill never lowers the target. Vague caller words ("consistently", "competition-ready") resolve to numbers in the skill; the service holds no hidden threshold.

Comparisons between candidates reuse one fixed base seed. The seed fixes the keyed start order exactly. Each card copy takes its opening library position from a key over the run seed, the `oracle_id`, and the copy index. Entry order has no effect, and after a swap the shared cards keep their relative order. A later shuffle (mulligan, fetch, search) matches the two decks only in part, because Fisher–Yates runs over a library that differs.

Commander alternatives is the one recommendation flow that earns a service query, because it contains no judgment at all: rank commander-role-legal candidates by how many of the existing 99 they retain, where "preserve color identity" is the retention metric itself — a card is lost iff its color identity escapes the candidate's or it has since been banned, each loss carrying its citation. Ties break by color-identity closeness to the original commander (else every five-color commander floods the top), then `edhrec_rank`. Doing this skill-side would mean the agent hand-computing color-identity set math over a hundred cards — exactly the recalled-not-grounded arithmetic the principles ban. Function-similarity re-ranking of the structural shortlist stays agent-side.

One consequence binds the goldfish engine: the result envelope gains a DSL-coverage field (defined-vs-inert counts plus the uncovered-card names). The engine only executes staples, so a candidate deck's floor is partly a statement about authoring coverage, not deck quality — and a loop optimizing an unexplainable floor would silently learn to prefer covered cards. Coverage in the envelope keeps every floor attributable and doubles as demand evidence for the staple cut's deck-under-test lane.

**Note (2026-09-30, ADR 0011 cutover):** engine coverage replaces DSL coverage. The envelope lists the cards the engine cannot run and the cards without a full card feature profile, so a floor stays attributable without the DSL.

**Amendment (2026-10-04, [ADR 0012](0012-arena-brawl-formats.md)):** the commander-alternatives query runs in the request's format. `edhrec_rank` becomes the format's popularity order, and a card outside the format's pool is a loss (`not_legal`).
