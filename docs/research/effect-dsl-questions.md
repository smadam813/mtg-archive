# Effect DSL: answers to the five prototype questions

**Question:** the Effect DSL prototype proposed a closed six-primitive vocabulary, a definitions-declare/policy-decides choice seam, structurally derived rules categories, and checks as the admission gate — and asked five questions before the engine moves into the real codebase.

**Answer:**

1. **Closed primitive vocabulary: keep it.** Forge — the only closed-vocabulary system proven at full-MTG scale — covers ~33,700 card scripts with ~200 primitives that grew by ~7/year for 12.5 years and never collapsed into a general language, while XMage's fully general Java converged on a shared effect library anyway. Plan for slow permanent growth; prefer parameters and composition before new primitives.
2. **The seam is right.** Every primary precedent examined — the Comprehensive Rules themselves, Stanford GDL/GGP, XMage, AlphaZero — puts legality in the game description and choice in a separate player/policy. Forge, the one system that leaked policy into card data, pays for it in 2,460 annotated card files and per-card AI code. Phrase it as one policy *interface* with swappable implementations, and ban AI-hint fields from the schema outright.
3. **Reading review works for surface facts but cannot be the gate** *(owner to confirm by reading)*: the one-field-per-Oracle-phrase mapping makes wrong-zone/missing-tapped errors visible to a reader, yet Forge shipped exactly that bug past a reviewer who had the Oracle text on the same screen — and primitive semantics are invisible in the JSON entirely.
4. **Separate fixtures, enforced pairing.** The prototype already stores checks as separate card-keyed objects with their own schema, whatever the announcement said; the precedents show the load-bearing choice is whether the toolchain enforces the pairing, not where the file lives. Keep two schemas; make the staple-set gate reject any definition without a passing check.
5. **The showcase interactions are correct, and the audit found three engine fixes to make before the goldfish engine inherits this code** *(whether anything felt wrong in hand remains the owner's to report)*: a Brainstorm put-back soft-lock, no way to decline a quality-constrained search, and engine-chosen mana payment that violates the prototype's own seam.

All facts below were verified against primary sources on 2026-08-23 and 2026-08-24. Live values (file and commit counts, card texts, rulings) were fetched directly from GitHub, Scryfall, and the Comprehensive Rules on those dates; prototype engine behaviors were verified by executing the engine block extracted from the prototype HTML headless under Node, with nothing in the repo modified.

## 1. Closed primitive vocabulary vs. a general effect language

> Is a closed primitive vocabulary the right choice, or do you want a more general effect language? The closed set trades expressiveness for verifiability and LLM-writability.

The closest prior art is Forge, a full-rules MTG engine that encodes its entire card pool as plain-text data scripts written against a closed keyword vocabulary — 33,666 `.txt` card scripts under [`forge-gui/res/cardsfolder`](https://github.com/Card-Forge/forge/tree/master/forge-gui/res/cardsfolder) on master (counted 2026-08-24 via `git ls-tree` on a treeless clone). [Sol Ring's complete script is five lines](https://raw.githubusercontent.com/Card-Forge/forge/master/forge-gui/res/cardsfolder/s/sol_ring.txt): `A:AB$ Mana | Cost$ T | Produced$ C | Amount$ 2 | …` — `AB$ Mana` names one API from the closed set, and everything else is parameters. The closed set itself is the [`ApiType` Java enum](https://raw.githubusercontent.com/Card-Forge/forge/master/forge-game/src/main/java/forge/game/ability/ApiType.java): 201 constants on master (including ~7 internal entries like `BlankLine`), each bound to a Java effect class, with closure enforced by a hard failure — `smartValueOf()` throws a `RuntimeException` for any script naming an unknown API, so an out-of-vocabulary card cannot load.

That vocabulary grows but does not explode. The same enum had [118 constants in the earliest retained commit (2014-01-20)](https://raw.githubusercontent.com/Card-Forge/forge/18e96a10283c7d8bae827b2964043b81a02a3c43/forge-game/src/main/java/forge/game/ability/ApiType.java) against 201 today — roughly 7 new primitives per year across 131 commits to the file, the latest dated 2026-08-23 — and new entries track new mechanics (`RingTemptsYou`, `Venture`, `Incubate`, `AssembleContraption`). Most expressiveness pressure is absorbed below the primitive layer: [Demonic Tutor](https://raw.githubusercontent.com/Card-Forge/forge/master/forge-gui/res/cardsfolder/d/demonic_tutor.txt) (tutor) and [Rampant Growth](https://raw.githubusercontent.com/Card-Forge/forge/master/forge-gui/res/cardsfolder/r/rampant_growth.txt) (ramp) are both single `SP$ ChangeZone` scripts differing only in parameters — the same move the prototype's `search_library` already makes for Evolving Wilds — and [Brainstorm](https://raw.githubusercontent.com/Card-Forge/forge/master/forge-gui/res/cardsfolder/b/brainstorm.txt) chains `Draw` into a second `ChangeZone` via `SubAbility`/`SVar` rather than needing new syntax. Even [Pithing Needle's mana-ability exception is expressed structurally inside the closed vocabulary](https://raw.githubusercontent.com/Card-Forge/forge/master/forge-gui/res/cardsfolder/p/pithing_needle.txt) (`ValidSA$ Activated.!ManaAbility` on the static mode) — the same move as the prototype's structurally derived mana abilities.

XMage takes the opposite, fully general approach — every card is a hand-written Java class, and [its readme claims over 32,000 unique cards implemented](https://raw.githubusercontent.com/magefree/mage/master/readme.md) at that approach's full scale. But the general language converged on a de-facto primitive library anyway: [Brainstorm's entire implementation is one call to a shared `BrainstormEffect`](https://raw.githubusercontent.com/magefree/mage/master/Mage.Sets/src/mage/cards/b/Brainstorm.java), while edge-case cards pay the general-language cost — [Pithing Needle needs an 80-line file](https://raw.githubusercontent.com/magefree/mage/master/Mage.Sets/src/mage/cards/p/PithingNeedle.java) with a bespoke `ContinuousRuleModifyingEffectImpl` subclass intercepting `ACTIVATE_ABILITY` events. Those edge cards are precisely the ones mtg-archive deliberately leaves inert. Fireplace (Hearthstone) is the hybrid and the closest analog to that inert-by-default design: [authoritative card data lives in `CardDefs.xml`, an optional per-card declarative script is merged in at load time, and a card with no script gets an empty scripts class](https://raw.githubusercontent.com/jleclanche/fireplace/master/fireplace/cards/__init__.py) — it still exists and plays with data-only semantics, against a fixed slot vocabulary (`activate`, `deathrattle`, `draw`, …).

Two framing facts complete the picture. What keeps authoring verifiable at scale in both MTG engines is automated checking layered on top of the encoding, not the encoding alone: XMage runs [`VerifyCardDataTest`](https://raw.githubusercontent.com/magefree/mage/master/Mage.Verify/src/test/java/mage/verify/VerifyCardDataTest.java) cross-checking every implemented card against MTGJSON reference data down to ability text, and Forge runs [scenario simulation tests](https://raw.githubusercontent.com/Card-Forge/forge/master/forge-gui-desktop/src/test/java/forge/ai/simulation/GameSimulationTest.java) (2,856 lines) that set up a game, resolve an ability, and assert the resulting state — the same shape as the prototype's per-definition checks. And full MTG semantics are formally unbounded — [optimal play is at least as hard as the Halting Problem](https://arxiv.org/abs/1904.09828) (Churchill, Biderman & Herrick) — so every practical encoding, closed or general, is necessarily a subset of the game; the design question is only where the boundary sits, not whether one exists.

**Recommendation.** Keep the closed vocabulary, with three provisions borrowed from the prior art. (1) Expect it to grow slowly and permanently rather than stay fixed — Forge went ~118 → ~201 over 12.5 years while covering ~33,700 scripts and never pivoted; growth arrives per new mechanic, exactly the "expressiveness grows by adding engine primitives" plan. (2) Before adding a primitive, prefer Forge's two escape valves: richer parameters on an existing primitive, and explicit composition (their `SubAbility`; the prototype's `effects` list). (3) Keep both enforcement layers: a hard failure on unknown primitive names (Forge's thrown exception *is* the closure mechanism) and per-definition executable checks (both engines needed them; encoding alone never guaranteed correctness at scale). The general-language alternative is not evidenced to buy much: XMage pays for generality only on edge cards this project leaves inert, and Fireplace independently validates inert-by-default. The Turing-completeness result reframes "closed vs. general" as "explicit boundary vs. implicit boundary" — and for LLM authorship gated by schema validation, an explicit boundary is the one you can check.

**Caveats.** The 33,666 figure includes variant/alternate-state scripts, so it slightly overstates unique names; the 201/118 counts come from the same regex over each enum version, and 201 includes ~7 internal entries. The GitHub repo's history starts in 2014 but Forge predates it, so the growth rate is an estimate over a truncated window. All three precedent projects target full rules-enforcement engines with adversarial play — their vocabulary sizes are upper bounds for the far narrower tier-2 goldfish scope, not predictions — and none used LLM authorship, so this research cannot say how well an LLM writes either format. Whether the closed set *feels* right to author and review is the owner's taste call; this gives the scale data to decide with.

## 2. The seam: definitions state what is legal, one policy makes every choice

> Is the seam right: definitions state what is legal, and one policy module makes every choice?

The Comprehensive Rules are themselves written on this seam. In [CR 601](https://media.wizards.com/2026/downloads/MagicCompRules%2020260819.txt), every choice made while casting a spell is assigned to the player ("the player announces the mode choice", 601.2b; "The player announces their choice of an appropriate object or player for each target", 601.2c) while the game's only job is verification ("The game checks to see if the proposed spell can legally be cast", 601.2e). The [Stanford Game Description Language](http://ggp.stanford.edu/readings/gdl_spec.pdf) specifies games purely as a legality relation — `legal(player, move)` "holds for player-move combinations allowed by the game rules", and a separate relation records the moves players actually make — and in the [GGP architecture](http://ggp.stanford.edu/readings/gdl_spec.pdf) the choosers are entirely separate programs: the Game Master holds the description and verifies legality, independent player programs make every choice. [AlphaZero](https://arxiv.org/abs/1712.01815) demonstrates the architectural ceiling of the same separation: with the rules as the only game-specific input, the policy alone was upgraded to superhuman without touching the rules description.

Forge violates the seam, at scale, and pays for it. AI policy hints are embedded directly in card scripts — [Daze carries `AILogic$ MinCMC.4` on its ability line](https://raw.githubusercontent.com/Card-Forge/forge/master/forge-gui/res/cardsfolder/d/daze.txt), and GitHub code search counts 2,460 card script files containing `AILogic` (2026-08-24). [Forge's Demonic Tutor script](https://raw.githubusercontent.com/Card-Forge/forge/master/forge-gui/res/cardsfolder/d/demonic_tutor.txt) — one of this prototype's own five staples — shows the cost: the tutor-choice policy is hardcoded, admitted weak in a TODO inside the card file, and the card carries `AI:RemoveDeck:Random` excluding it from AI decks because the AI cannot pilot it. The coupling is bidirectional and grows per card: 107 Java files in the forge-ai module branch on `AILogic` strings, including [card-name-specific string dispatch into per-card AI classes](https://raw.githubusercontent.com/Card-Forge/forge/master/forge-ai/src/main/java/forge/ai/ability/DigAi.java) (`if ("MadSarkhanDigDmg".equals(sa.getParam("AILogic")))`). XMage keeps the seam clean on both sides: [its Demonic Tutor class is pure structure with zero AI references](https://raw.githubusercontent.com/magefree/mage/master/Mage.Sets/src/mage/cards/d/DemonicTutor.java), and all choice-making lives in [`ComputerPlayer`](https://raw.githubusercontent.com/magefree/mage/master/Mage.Server.Plugins/Mage.Player.AI/src/mage/player/ai/ComputerPlayer.java), a Player implementation explicitly documented as the swappable parent class for any AI.

The seam is also what makes this project's own principle operational: "lower bounds, honestly labeled" already locates play skill in the policy, and the prototype's engine treats a choice as just another action applied to state (`if (action.type === "choose") return resolveChoice(state0, action.pick)`), so a greedy policy, a human, or a stronger future policy can drive identical definitions and only the reported floor changes.

**Recommendation.** Keep the seam exactly as prototyped, with two refinements. First, phrase it as one policy *interface* with many interchangeable implementations rather than literally one module — GGP runs arbitrary player programs against one description, and XMage's `ComputerPlayer` is explicitly a base class for multiple AIs; that swappability is what lets the reported floor improve over time without touching a card definition, and it gives deterministic replays (a recorded sequence of choice resolutions replays against the same definitions). Second, make the Forge failure mode a hard schema rule: no AI-hint or annotation field ever enters a card definition, even as a convenience — the leak starts small (a parameter on Daze) and ends with per-card policy code; if a policy ever needs card-specific knowledge, key it by card name inside the policy module. CR 601 is the strongest precedent that the domain is naturally shaped this way: it enumerates choices and assigns each to "the player" while "the game" only checks legality — the prototype is a direct transcription of that structure.

**Caveats.** The evidence establishes precedent and one well-documented failure mode, not a proof; the final call is the owner's. Forge is not a strawman — it targets a full adversarial AI playing 25,000+ cards in real time with no pause-and-ask seam available, constraints a goldfish Monte Carlo engine does not share, so its `AILogic` design is a conscious trade under different pressure. The 2,460 and 107 counts are GitHub code-search totals on the default branch as of 2026-08-24 and drift with commits. The CR quotes are from the 2026-08-19 text, whose download URL is versioned and will rot; and the CR finding is an analogy — it assigns choices to human players in a paper game, not software modules. AlphaZero is cited only for the architectural point, not as evidence this project needs a learned policy.

## 3. Can you review an LLM-authored definition by reading the JSON?

> Can you review an LLM-authored definition by reading the JSON?

This one is ultimately the owner's to answer by reading; what follows is the evidence to read with.

The closed vocabulary maps field-for-field onto Oracle sentences. The prototype's Rampant Growth definition (lines 469–476) sits in one-to-one correspondence with [the official Oracle text](https://api.scryfall.com/cards/named?exact=Rampant+Growth) — "basic land card" = `filter`, "onto the battlefield" = `to`, "tapped" = `tapped: true`, "then shuffle" = `then_shuffle: true` — so a field-by-field diff is possible. And the Tab 6 mis-authored Rampant Growth *is* catchable that way, but only that way: the broken JSON (`to: "hand"`, no `tapped`, lines 504–511) is schema-valid and structurally identical to the legitimate Demonic Tutor definition (lines 461–468), so it reads as a plausible real card unless diffed against *this card's* Oracle sentence. The check that catches it (`CHECKS['Rampant Growth'][0]`, lines 1054–1059) asserts exactly the two Oracle clauses the mis-authoring violates — destination and tap state — which is what a per-clause check discipline looks like.

Two things reading cannot see. Part of Pithing Needle's semantics is not in its JSON at all: whether `except: "mana_abilities"` implements [the official ruling](https://api.scryfall.com/cards/776899f8-e977-42b7-8b54-6f726a349e3c/rulings) ("the mana ability can be activated but the other ability can't") depends on the engine's structural `isManaAbility` derivation and `activationLock` (engine lines 531–533, 625–634), not on any reviewable field. And there is a live rules divergence invisible in a "correct" definition: [official rulings on Rampant Growth](https://api.scryfall.com/cards/b7c47024-5e08-4b17-b41a-7647f8b814b9/rulings) say a search for a card with characteristics may fail to find ("you don't have to find the card if you don't want to"), but the prototype's `search_library` primitive offers only matching cards and whiffs only when zero match — no decline option exists (engine lines 696–716, 763–777). The gap is in the primitive, invisible in any definition that uses it.

Forge's track record calibrates what reading review is worth. Its card scripts embed the Oracle sentence in the same small file — [`rampant_growth.txt`](https://raw.githubusercontent.com/Card-Forge/forge/master/forge-gui/res/cardsfolder/r/rampant_growth.txt) carries `Tapped$ True` on the ability line and the Oracle text directly below it — which is what makes diff review possible at all. Reading has real yield: in [PR #5250](https://github.com/Card-Forge/forge/pull/5250) the reviewer caught many substantive script errors by reading diffs before merge ("wrong amount", "wrong restriction", "where's the payment?", "wrong rounding", "wrong tgts"). And yet the same PR shipped exactly the Tab 6 bug class: [White Orchid Phantom was added](https://github.com/Card-Forge/forge/commit/11d0c54023) with its search effect missing `Tapped$ True` even though two other lines of the same 10-line file — the trigger description and the Oracle line — both said "put it onto the battlefield tapped"; the mismatch was on-screen at review time, the reviewer commented inline on that very file, and the PR was approved. The bug was found two weeks later [by a player actually playing the card](https://github.com/Card-Forge/forge/issues/5346) — the fetched land entered untapped, precisely the failure Tab 6 simulates — and [fixed the same day by adding the one missing token](https://github.com/Card-Forge/forge/commit/6a672eedb5). One further practical fact: ground truth drifts — the prototype's embedded `ORACLE` strings for [Pithing Needle](https://api.scryfall.com/cards/named?exact=Pithing+Needle) and [Evolving Wilds](https://api.scryfall.com/cards/named?exact=Evolving+Wilds) are older official wordings than current 2024+ self-referential templating ("As this artifact enters…"), substantively identical but a source of spurious diffs unless the Oracle snapshot is pinned.

**Recommendation.** Treat reading review as a productive first pass and the checks as the actual admission gate, and structure both around the Oracle diff: (1) require every definition to carry, or be reviewed beside, its pinned Oracle text — Forge's same-file convention is what makes the field diff possible, so adopt it rather than relying on reviewer memory; (2) keep the vocabulary closed and one-field-per-Oracle-phrase, since that property is why the broken definition is visible to a reader at all; (3) do not trust the reading pass even when the mismatch is on-screen — White Orchid Phantom shows a competent, engaged reviewer approving this exact bug class — so require each check suite to assert every Oracle clause (destination, tap state, shuffle, count); `CHECKS['Rampant Growth'][0]` is the template; (4) accept that reading cannot see primitive semantics: gaps like decline-to-find must be closed by testing the primitives themselves — engine-level fixtures per primitive, a separate suite from per-card checks, worth adding to the goldfish-engine ticket.

**Caveats.** Whether the owner personally can review these definitions by reading is a skill-and-taste judgment only the owner can make, and a different reviewer may weight the difficulty differently. The Forge evidence is one well-documented miss/catch pair plus one PR's review thread, not a systematic study — and Forge's vocabulary is far larger than the prototype's six primitives, so the prototype should be strictly easier to review. Scryfall is treated as primary for Oracle text and rulings (it serves WotC's official data verbatim). Prototype line numbers refer to `prototypes/effect-dsl/effect-dsl-prototype.html` on branch `prototype/effect-dsl`.

## 4. Should checks live inside the definition or in separate fixture files?

> Should `checks` live inside the definition (as prototyped) or in separate fixture files?

The premise needs correcting first: despite the announcement's phrasing that every definition "carries" checks, the prototype's definition objects contain only `{ name, abilities }` — checks live in a separate `CHECKS` table keyed by card name (lines 454–501 vs. 1047–1097), a distinct object with a distinct schema in the same file. The colocation claim exists only in a comment. And the prototype's own mis-authoring demo depends on that separation: `runCheck(def, check)` takes the definition as a parameter (lines 1099–1102), which is what lets the stock Rampant Growth fixture be reused unchanged against the broken definition (line 1541) — a reuse only possible because checks are keyed to card identity, not embedded in the object they validate. Sizes point the same way: checks are as large as or larger than the definitions they verify (Pithing Needle: 7 definition lines, 15 check lines), and fixtures reference other corpus cards (Brainstorm's check seeds the library with four other cards), so inlining would at least double each LLM-emitted object and make every definition textually depend on cards outside itself. The check DSL is also already a second schema under its own growth pressure: the one static-ability check needed an escape hatch outside the declared given/when/then vocabulary ("this check is special-cased below: it asserts on legalActions, not on state", lines 1087, 1106–1120).

The precedents decompose the question. Rust's doctests are the colocation flagship, and their stated purpose is anti-drift: [rustdoc executes documentation examples as tests](https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html) so that "examples within your documentation are up to date and working", and [the Rust book names the failure mode this prevents](https://doc.rust-lang.org/book/ch14-02-publishing-to-crates-io.html) — "nothing is worse than examples that don't work because the code has changed since the documentation was written." But the guarantee comes from the toolchain refusing to skip the checks, not from the file location. The [JSON Schema Test Suite](https://github.com/json-schema-org/JSON-Schema-Test-Suite/blob/main/README.md) — the canonical separate-fixture project — separates for reuse across many consumers, yet within each fixture the subject schema is embedded alongside its tests in one object, and the suite [formally schema-validates its own fixture format](https://github.com/json-schema-org/JSON-Schema-Test-Suite/blob/main/README.md) (`test-schema.json`) with sanity-check CI guaranteeing invariants over all fixture files — precedent for a test DSL as its own formally specified schema. [Fireplace keeps card implementations and tests in separate parallel trees](https://github.com/jleclanche/fireplace/blob/master/tests/test_classic.py) (one named test function per covered card) plus [a whole-database structural gate iterating every card definition](https://github.com/jleclanche/fireplace/blob/master/tests/test_carddb.py) — but nothing forces a new card script to ship with a behavioral test. Forge shows that unenforced pairing at scale: [its master tree](https://api.github.com/repos/Card-Forge/forge/git/trees/master?recursive=1) holds 33,666 card-script files against 116 test files total, and [the test harness merely points at the card data directory](https://github.com/Card-Forge/forge/blob/master/forge-gui-desktop/src/test/java/forge/card/CardMockTestCase.java) — the overwhelming majority of card scripts ship with no card-specific test, which is exactly how a White Orchid Phantom reaches players (§3).

**Recommendation.** Keep checks structurally separate from the definition object — as the prototype already does — and make the gate, not the file layout, carry the guarantee. Three independent choices: (1) two schemas, not one — the card-semantics object the LLM emits stays small (5–9 lines per card), and the check DSL, which already needed an escape hatch and will grow its own assertion vocabulary, gets its own formal schema as the JSON Schema Test Suite does; (2) pairing by card identity, enforced at admission — the Rust lesson is that checks stay honest because the toolchain refuses to skip them, the Forge lesson is the inverse failure, so the staple-set gate should reject any definition lacking at least one passing check, making "exists unchecked" impossible regardless of layout; (3) definition-independence is worth keeping — `runCheck(def, check)` with name-keyed fixtures lets the same fixture reject a re-authored or adversarially broken definition, lets a different agent author or review checks than authored the definition, and lets checks reference other corpus cards without bloating the emitted object. Whether the paired check rides in the same file or a sibling `fixtures/` file is packaging, and the evidence is genuinely indifferent on that residue once the gate enforces pairing — that part is the owner's taste.

**Caveats.** The Forge coverage figures are tree-shape evidence from the 2026-08-24 master snapshot; a harness living outside `src/test` naming conventions would be missed, though code search surfaced none. All four precedent projects have human authors — none addresses the one-shot-LLM-emission cost of a bloated object directly; that part of the trade-off is reasoned from the prototype's measured sizes. The rustdoc analogy is imperfect: doctests are colocated because they *are* the documentation's examples, one text serving two roles, which the DSL's checks are not — weakening the colocation half of the analogy and strengthening its enforcement half.

## 5. Did anything feel wrong while you clicked?

> Did anything feel wrong while you clicked — an unexpected state, a missing action, an extra action?

The question is about the owner's experience at the table, which only the owner can report. What research can contribute is a headless audit of the engine against [the Comprehensive Rules of 2026-08-19](https://media.wizards.com/2026/downloads/MagicCompRules%2020260819.txt), enumerating the divergences most likely to register as feel anomalies. For balance, the showcase interactions all check out against primary sources: fetched basics enter tapped per the Oracle text, Evolving Wilds' sacrifice is paid as a cost before the effect runs, the library shuffles even on a whiffed search, the land drop is once per turn, and the Needle/Sol Ring/Evolving Wilds lock triangle matches [the Scryfall rulings](https://api.scryfall.com/cards/776899f8-e977-42b7-8b54-6f726a349e3c/rulings). All 7 checks in the engine's `CHECKS` table pass headless and the deliberately broken Rampant Growth fails as intended (the announcement's "20 headless checks" presumably counts harness-level assertions; the engine table holds 7).

Two genuine bugs a clicker could hit. First, a missing action: when any card matches a quality-constrained search (Rampant Growth, Evolving Wilds), the engine forces the player to pick a match — there is no fail-to-find option, which [CR 701.23b](https://media.wizards.com/2026/downloads/MagicCompRules%2020260819.txt) explicitly grants ("that player isn't required to find some or all of those cards even if they're present"); a headless run confirms the pending options are exactly the matches with `legalActions()` empty until one is picked. (Demonic Tutor's forced find is correct — CR 701.23d makes quantity-only searches mandatory.) Second, a soft-lock: if Brainstorm resolves with a short library and the hand empties before both put-backs are done, the engine parks an unresolvable pending choice with zero options, `legalActions()` returns `[]`, and Brainstorm is stranded in no zone — where [CR 609.3](https://media.wizards.com/2026/downloads/MagicCompRules%2020260819.txt) says the impossible remainder is simply skipped ("does only as much as possible"). The cause is the put-back branch re-pending without re-checking hand size (engine lines 787–795), unlike the initial guard.

One seam violation the owner will feel in free play: mana payment is auto-solved by a greedy solver instead of surfacing as a choice point, so the engine taps lands the pilot never would — [CR 601.2g](https://media.wizards.com/2026/downloads/MagicCompRules%2020260819.txt) makes activating mana abilities during payment the player's decision, and the prototype's own principle is that definitions declare choices and the policy decides. In a headless run, casting Demonic Tutor `{1}{B}` off `[Island, Swamp, Swamp]` taps Swamp + Island, leaving Brainstorm in hand dead this turn where a pilot taps the second Swamp; the code acknowledges it ("the real pilot policy owns this later", engine line 564).

Latent divergences worth recording now. The structural derivation `isManaAbility` ("activated AND every effect is `add_mana`") is narrower than [CR 605.1a](https://media.wizards.com/2026/downloads/MagicCompRules%2020260819.txt) ("could add mana… when it resolves", no target, not loyalty, no library movement), so a future staple whose mana ability carries a rider — Ancient Tomb-style "Add {C}{C}. This deals 2 damage to you" — would lose its Needle exemption and be wrongly lockable; for the six prototype cards the derivation gives the CR-correct answer in every case. The prototype's Needle also only checks battlefield permanents and offers only the 10-card corpus as nameable options, where [the real card affects sources in every zone and can name any card](https://api.scryfall.com/cards/776899f8-e977-42b7-8b54-6f726a349e3c/rulings) — currently unobservable, since no off-battlefield activated abilities exist in the DSL. The timing collapse is mostly sound for goldfishing, with two edges off the CR: the mana pool persists for the whole turn ([CR 106.4](https://media.wizards.com/2026/downloads/MagicCompRules%2020260819.txt) empties it each step and phase) and instants are indistinguishable from sorceries (CR 117.1a) — while the immediate no-stack resolution of mana abilities matches CR 605.3b exactly. Loss conditions are logged but never enforced: an empty-library draw prints "(A real game is lost here.)" and play continues, with `state.over` written only in the initializer, where [CR 704.5b](https://media.wizards.com/2026/downloads/MagicCompRules%2020260819.txt) ends the game as a state-based action. And one internal inconsistency: permanents put onto the battlefield by `search_library` skip "enters" abilities — the `resolveChoice` branch pushes the permanent directly without calling `runEnters` (engine lines 771–774) while the cast and play-land paths both call it — unobservable while only basics are fetched, wrong the moment a fetchable permanent with an enters ability joins the staple set.

**Recommendation.** The prototype's rules instincts are right where it aimed, so the DSL shape itself is not impugned by this audit. Three changes before the goldfish engine inherits the code: (1) fix the put-back re-pend to re-check hand size (CR 609.3) — it is a soft-lock; (2) add a decline/fail-to-find affordance to quality-constrained searches (CR 701.23b) — cheap now, load-bearing later, because "fetch or hold" is exactly the line a pilot policy must be allowed to take; (3) promote mana payment from the greedy solver into a declared choice point resolved by the pilot policy — the prototype's own seam applied to itself, with the greedy solver as the default policy (which also serves "lower bounds, honestly labeled": greedy payment under-reports castability). Separately, re-derive `isManaAbility` from CR 605.1a's actual criteria rather than every-effect-adds-mana, or Ancient Tomb-class staples will be wrongly Needle-lockable when added. The timing collapse, unenforced game-over, and battlefield-only Needle scope are fine as labeled simplifications — record them in an explicit "known divergences from CR" list next to the DSL so future click-feel anomalies can be triaged against it.

**Caveats.** The two divergences the owner most plausibly hit in free play are the auto-tapped wrong lands and a search list with no decline; the soft-lock needs a 1–2 card library, which none of the five scripted walkthroughs sets up. Sheoldred's absent triggers, the closed six-primitive vocabulary, and the 10-card corpus are the announced design under review, so they were not audited as divergences. `state.onThePlay` is dead code (set, never read) but harmless for the Commander target — CR 103.8c has no first-draw skip in multiplayer games other than Two-Headed Giant. Locked abilities still appear as disabled buttons with the lock reason, which under the CR would simply not be legal actions — it reads as a deliberate, effective pedagogical display rather than a bug. Everything cited was verified by executing the engine block extracted from the prototype HTML under Node; nothing in the repo working tree was modified.
